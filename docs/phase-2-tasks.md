# Phase 2 — Versioning, pipeline, explanations

Phase 1's engine runs inside a real claim lifecycle: contracts pin a plan version, ops versions are selected by `asOf`, claims move through a state machine, decisions are re-adjudicated by supersession, and every decision renders a claimant letter and a file note from its stored trace. No evidence documents, overrides, authority sign-off or payment in this phase (Phase 3). No UI (Phase 4).

- [ ] **2.1 Trace v1 (decide first).** The `/0` trace stores only `{ruleId, result, missing}` per rule. P0-5 also needs the deciding row, the facts read with their values, the reason code and the clause, and P0-2 needs version selection as a traced step. Record the shape in `docs/decisions.md` (D34), bump to `adjuster.trace/1`, regenerate every GC fixture, `fixtures:check` OK, and keep `decisions:verify` green on the reseeded decisions. `/0` decisions stay replayable or are reseeded: say which in D34.
- [ ] **2.2 Fixtures for this phase.** Decisions first (D35): `plan-v2` (default: one Essential deductible change, `effectiveFrom` after every GC contract's purchase date) and `ops-v2` (default: system authority limit change). The oracle then produces GC-12, GC-13, GC-14 (engine-level), RV-01 (same claim facts under a v1 and a v2 contract), VP-02..VP-04 (contract + `asOf` → selected versions or no decision), and PL-06 (contract not found short-circuits; new ID). `rules:lint` and `fixtures:check` OK.
- [ ] **2.3 Contract and Claim tables.** `Contract` is seeded and read-only (trigger), and pins a published `planVersionId` at purchase. `Claim` holds `status` and `paymentStatus` as separate fields (the outcome stays on `Decision`). `Decision.claimId` becomes an FK. Synthetic seed only.
- [ ] **2.4 Version selection.** A pure `selectVersions(contract, versions, asOf)`: plan from the contract pin (never the date of loss, the date reported or the latest version), and ops as the latest published version effective on `asOf`. With no effective version there is no decision and a coded error. The selection is written into the trace. VP-02..VP-04 pass.
- [ ] **2.5 Claim state machine.** A transition table in code, with statuses from domain brief §7. An illegal transition throws (PL-01) and every transition is audited. Phase 2 exercises `OPEN → IN_REVIEW → PENDING_EVIDENCE | REFERRED | DECIDED`, `WITHDRAWN` and `CLOSED`; the rest of the table is written now and exercised in Phase 3.
- [ ] **2.6 Pipeline.** `adjudicateClaim(db, claimId, asOf)` loads the claim and contract, short-circuits on contract not found (PL-06, the seam left in 1.11), selects the versions, freezes the snapshot, runs the engine, then records the decision and the status transition in one transaction. Mapping: DENY/APPROVE/PARTIAL → `DECIDED`, PEND → `PENDING_EVIDENCE`, REFER/GAP → `REFERRED`. GC-01..10 and GC-12..14 pass through the pipeline. Fix the intermittently failing `inv-01-04-22-actions` once the pipeline tests run alongside it.
- [ ] **2.7 Re-adjudication.** An unchanged `inputHash` is a no-op that returns the existing decision (PL-02). Changed facts insert a superseding decision under the same plan version and the ops version current at `asOf` (PL-03). Publishing a version creates no decision rows.
- [ ] **2.8 RV-01 end to end.** Publish `plan-v2`. A contract sold after it gets the new outcome. Every existing decision is unchanged and `decisions:verify` stays OK. Add a check that a decision's plan pin equals its contract's pin, under an existing code (record which one in `decisions.md`) and with a tamper fixture.
- [ ] **2.9 Letter and note rendering.** Pure `renderLetter(trace)` and `renderNote(trace)` that only substitute placeholders: `{name}` from the trace, and an unknown placeholder throws. D32: only non-PASS rules appear. D24/D19: `claimantVisible: false` rules show neutral wording and flags never reach the letter. The letter shows the amount math line by line from the valuation steps. GC-04 and GC-14 letters cite both reasons with their clauses. GC-12's letter contains no flag ID or flag text. PL-05: re-rendering after publishing a version with different templates gives identical bytes.
- [ ] **2.10 Hand-recompute.** `tools/recompute_from_trace.py` (an oracle, not product code) reads only a stored explanation JSON and reproduces `payableCents` for every golden, including the null amounts on denials.
- [ ] **2.11 Seed and gate.** `seed:decisions` runs claims through the pipeline: GC-01..10 and 12..14, the RV-01 pair, and claims either side of `ops-v2`'s effective date. `decisions:verify:test` OK in CI. TM-01..TM-08 still each fail with exactly their own code.

**Exit criteria:** VP-01..VP-04, RV-01 and PL-01..PL-06 pass. GC-01..10 and GC-12..14 pass through the pipeline. Letters and notes render from the stored trace only. The hand-recompute script agrees on every golden. `decisions:verify` is OK across both plan versions and both ops versions, and CI enforces it. `grep` finds no plan name, tier or threshold under `src/`.
